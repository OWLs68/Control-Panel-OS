# /finish — закриття сесії Roma OS

Мета одна: наступний `/start` має підняти з репо все, щоб продовжити
роботу. Це **журнал**, а не звіт: дописуємо, не переписуємо. Коротко.

**Без аргументів.** Просто `/finish`. Повторний виклик у тій самій сесії
дописує в той самий блок, не створює новий і не переписує старе.

---

## 1. Межі сесії

`.claude/.session-runtime.json` → `session_id`, `start_head`. Немає файлу —
взяти з блоку «ПОТОЧНИЙ СТАН» у `HANDOFF.md`. Немає й там — `git log --since`
і сказати в звіті, що це наближення.

```bash
git log <start_head>..HEAD --oneline
git diff --stat <start_head>..HEAD
git status --short
```

Продуктовий код (`src/`, `index.html`, `style.css`, `sw.js`, `build.js`,
`server/`, тести, workflow) незакомічений → назвати в звіті, не комітити.

## 2. «ПОТОЧНИЙ СТАН» у `HANDOFF.md` — переписати, коротко

Це єдине місце, яке **переписується**, бо це стан, а не історія. ≤ 25 рядків:

```md
- session_id / started_at / branch / start_head / start_main / work_end_head
Де зупинились: 3–5 рядків, тільки факти, з посиланнями на профільні документи
Blockers: … або «Немає.»
Наступний крок: 1–3 рядки
Чекає Романа: нумерований список, без пояснень
```

`work_end_head` — HEAD до службових docs-комітів `/finish`. Поточний HEAD
у документах не зберігається ніколи — `/start` бере його з git.

## 3. `SESSION_LOG.md` — дописати

Один блок на сесію, зверху файлу, **≤ 40 рядків**:

```md
## YYYY-MM-DD — <session_id> — тема в пʼять слів

- Зроблено: пункт = один рядок, з комітом або документом, де деталі
- Рішення Романа: …
- Інциденти: … (або «Без інцидентів.»)
- Відкрито / далі: …
Branch · Start HEAD · Work end HEAD · verify/e2e/CI одним словом · deploy
```

Блок уже є → додати рядок `### Доповнення HH:MM` і нові пункти під ним.
Деталі (числа, мапи, причини) живуть у `PORTING.md`, `GATEWAY.md`,
`ISSUES.md`, `STAGE-1.md` — журнал лише посилається на них.

Так само коротко: `ISSUES.md` (новий баг → `open`; виправлено → `fixed` +
коміт; **перевірено** там, де проявлявся → `verified`), `STAGE-1.md`
(що перестало бути заглушкою, нове для телефона), `PORTING.md` (тільки
при реальному переносі). `CLAUDE.md` — не писати; нове правило →
запропонувати патч і чекати «так».

## 4. Коміт і push

```bash
git add docs/ .claude/commands/
git commit -m "docs(session): <session_id>"
git push -u origin <гілка>     # retry 2/4/8/16s
```

Не `main`, не merge, не deploy, не force, не reset.

## 5. Тести і CI — тільки якщо мінявся продуктовий код

```bash
git diff --stat <start_head>..HEAD -- src index.html style.css sw.js build.js server tests .github
```

- **Порожньо (лише документи)** → тестів не ганяти, CI не чекати. Кінець.
- **Не порожньо, і останній CI на `work_end_head` уже зелений** (за HOT RULE 3
  код зазвичай уже в `main` із зеленим CI) → теж нічого не ганяти. Кінець.
- **Не порожньо і CI ще не було** → `npm run verify` і `npm run e2e`, тоді
  один запит `list_workflow_runs` (`ci.yml`, фільтр `branch`, `perPage: 1`),
  чекати інструментально до 5 хв. `failure` → причина в `ISSUES.md`, runtime
  не видаляти, звіт із «CI червоний». Timeout → сказати, що прогін ще йде,
  runtime не видаляти. Ніколи не завершувати хід словами «чекаю CI».

## 6. Runtime-файл і звіт

Документи закомічені й запушені, і CI (якщо він був потрібен) зелений →
`rm -f .claude/.session-runtime.json`. Інакше файл лишається — це те, що
дозволяє доробити ту саму сесію, а не почати нову поверх.

Звіт ≤ 8 рядків українською: що записано, `verify/e2e/CI` або «код не
мінявся», що чекає Романа, `Branch / work_end_head / main не чіпався`.

## Якщо щось пішло не так

Конфлікт при push → `git pull --rebase origin <гілка>`, вирішити руками,
пушити знову. Сесія без комітів → блок у журналі з «Код не чіпали».
