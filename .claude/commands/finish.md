# /finish — закриття сесії Roma OS

Викликається, коли сесія логічно завершена і репозиторій треба підготувати
до наступного чата. **Ідемпотентна:** повторний виклик тієї самої сесії
оновлює вже створені записи, а не плодить дублі.

**Без аргументів.** Просто `/finish`.

**Що робить:** оновлює службову документацію так, щоб наступний `/start`
підняв повний контекст із репо. Handoff живе в git, не в чаті й не в Drive.

---

## PHASE 0 — RECOVERY FIRST

> Робиться **першим**, до будь-якого аналізу. `/finish` часто викликається
> вже на високому використанні контексту, а cloud-контейнер ефемерний:
> локальний коміт помре разом із ним, тому найцінніше йде в git **і на remote**.

1. Прочитати `.claude/.session-runtime.json`. Якщо файлу немає — відновити
   межі з блоку «ПОТОЧНИЙ СТАН» у `HANDOFF.md` (там ті самі поля), а якщо
   і його немає — створити як на `/start`, зазначивши це в звіті.
2. Оновити блок «ПОТОЧНИЙ СТАН» зверху `HANDOFF.md`:

```md
- session_id: …
- started_at: …
- branch: …
- start_head: …
- start_main: …
- work_end_head: …
- Де зупинились: …
- Blockers: … (або «Немає.»)
- Наступний крок: …
- Чого не чіпати: …
- Чекає рішення Романа: … (або «Нічого.»)
```

3. Checkpoint-коміт **тільки docs**: `git add docs/ && git commit`.
4. **Push одразу:** `git push -u origin <гілка>`, retry 2/4/8/16s.
   Не `main`, не merge, не deploy.

> **`work_end_head` — не «поточний HEAD».** Це HEAD **до** службових
> docs-комітів `/finish`. Документ, який сам комітиться, не може містити
> хеш власного коміту: записав → змінив файл → коміт отримав інший хеш.
> Тому поточний HEAD у документі не зберігається взагалі — `/start` бере
> його фактично, через `git rev-parse HEAD`. Не ганятись за власним хешем
> додатковими комітами.

**На Phase 0 не називати DONE те, що не перевірено.** Якщо робота не
прогнана через verify/e2e — писати «зроблено, не перевірено».

## PHASE 1 — ЗБІР СТАНУ, ОДИН ПРОХІД

Один прохід по сесії → внутрішня чернетка. **Не** робити окремий аналіз
під кожен документ.

Категорії: зроблено · обговорено без виконання · рішення · рішення Романа ·
інциденти · blockers · відкладено · відкриті питання.

Git-діапазон сесії — **завжди** зі `start_head`:

```bash
git log <start_head>..HEAD --oneline
git diff <start_head>..HEAD --stat
git status --short
git merge-base --is-ancestor HEAD origin/main && echo "HEAD вже в main"
git fetch origin main && git rev-parse origin/main   # чи зсунувся від start_main
```

> `git log <гілка> --not main` **не використовувати**: робоча гілка може
> бути вже змержена в `main`, і команда покаже нуль комітів.

**Режим:** шукати `session_id` у `SESSION_LOG.md`.
Немає → CREATE. Є → UPDATE (оновлювати той самий блок).

---

## PHASE 2 — SANITY CHECK

Перед тим як щось позначити DONE — звірити з фактичним кодом і git, а не
з текстом документації.

- Якщо в документі висить `⏳ треба перенести modal`, а modal уже
  перенесений — **видалити застарілий рядок**, а не дописувати `✅` поруч.
- Заборонено одночасно `TODO X` і `DONE X`.
- Самоперевірка: «чи лишився десь ⏳ або „лишилось" для того, що я цієї
  сесії позначив зробленим?» Якщо так — видалити той рядок.

## PHASE 3 — ЗАПИС

### `docs/roma-os/SESSION_LOG.md` — завжди

Нові сесії зверху. Секція «Інциденти» присутня завжди; якщо нічого не
було — рівно `Без інцидентів.`

```md
## YYYY-MM-DD — <session_id> — коротка тема

### Зроблено
### Обговорено
### Рішення
### Інциденти
### Відкладено
### Відкриті питання

### Метрики
Branch: · Start HEAD: · Work end HEAD: · Commits: · CI: · Deploy:

Ні HEAD, ні номер прогону CI в метриках не фіксуються як канонічні —
`/start` бере і те, і те фактично. Тут — тільки підсумок словами.
```

UPDATE-режим дописує в цей самий блок, новий не створює.

### `docs/roma-os/ISSUES.md` — коли релевантно

- новий баг (з iPhone або з CI) → додати запис, `status: open`
- виправлено в коді → `fixed` + `fix commit`
- **реально перевірено** → `verified`

`verified` не ставити тільки тому, що код написано. Баги з iPhone і CI
живуть тут, а не в `SESSION_LOG.md`.

**Межа зі STAGE-1:** «ще треба перевірити на телефоні» → чекбокс у
`STAGE-1.md`. «Перевірили і знайшли конкретний дефект» → запис в `ISSUES.md`.
Не дублювати.

### `docs/roma-os/STAGE-1.md` — коли релевантно

Progress checklist · що перестало бути заглушкою · нове для перевірки на iPhone.

### `docs/roma-os/PORTING.md` — тільки при реальному переносі

Компонент реально перенесено з NeverMind → додати в «перенесено», прибрати
з черги, зафіксувати donor quirks (дивні значення, які чіпати не можна).

### `CLAUDE.md` — **не писати**

Побачив нове стабільне правило → **запропонувати короткий патч у звіті**
і чекати підтвердження. Без «так» не записувати.

### Коміт — обов'язково, до verify і push

Інакше написане лишиться тільки в робочій копії контейнера.

```bash
git status --short
git add docs/roma-os/SESSION_LOG.md docs/roma-os/ISSUES.md         docs/roma-os/STAGE-1.md docs/roma-os/PORTING.md         docs/roma-os/HANDOFF.md      # тільки ті, які /finish реально змінив
git commit -m "docs(session): finalize <session_id>"
```

Staged лише службова документація. **Продуктовий код `/finish` не комітить
автоматично** — якщо в робочій копії лишились зміни в `src/`, `index.html`,
`style.css`, `sw.js`, тестах чи workflow, назвати їх у звіті й лишити
Роману.

## PHASE 4 — VERIFY

```bash
npm run verify   # lint + типи + юніт-тести + сторож кордону + збірка
npm run e2e      # Playwright, окремо
```

`npm run verify` **не** містить E2E — запускати обидва.
Локально в cloud-сесії e2e йде здебільшого в Chromium; WebKit (двигун iOS)
вмикається тільки в CI.

---

## PHASE 5 — PUSH І CI

1. `git push -u origin <гілка>`, retry 2/4/8/16s при мережевих помилках.
2. Дочекатись CI на цій гілці (`mcp__github__actions_list`, `ci.yml`),
   ліміт очікування ~5 хв; далі звітувати фактичний стан.
3. **CI червоний → сесія НЕ завершена повністю.** Визначити причину
   (`get_job_logs`, `failed_only`). Реальна регресія → запис в `ISSUES.md`
   + відображення в «ПОТОЧНИЙ СТАН». Не писати «все зелено».
4. **Якщо після прогону CI щось дописувалось** в `ISSUES.md` чи `HANDOFF.md` —
   окремий docs-коміт **і push**. Інакше цей стан лишиться тільки локально,
   а наступна сесія підніме репо без нього.

### Прибрати runtime-файл — тільки при повному успіху

`.claude/.session-runtime.json` тримає `session_id` і `start_head`. `/start`
повторно використовує його, якщо файл на місці — тож залишений файл змусить
**наступну** сесію продовжити чужий ID і чужий `start_head`.

Видаляти локально (коміт не потрібен — файл gitignored) тільки коли зійшлось
усе разом:

- службова документація закомічена;
- гілка запушена;
- CI зелений;
- `HANDOFF.md` і `SESSION_LOG.md` фіналізовані.

```bash
rm -f .claude/.session-runtime.json
```

**Якщо `/finish` обірвався або CI червоний — файл НЕ видаляти.** Він і є
те, що дозволяє доробити цю саму сесію, а не почати нову поверх неї.

**МОЖНА:** комітити зміни docs/handoff, пушити поточну робочу гілку.

**НЕ МОЖНА автоматично:** merge в `main`, push у `main`, force push,
`git reset`, запускати production deploy, створювати pull request.

Push робочої гілки обов'язковий: наступна cloud-сесія отримує handoff
із репо, а не з цього контейнера.

## PHASE 6 — ЗВІТ

≤12 рядків українською, технічні терміни з поясненням у дужках:
зроблено · оновлені файли · перевірені й не змінені файли ·
`verify ✅ · e2e ✅ (N) · CI ✅/⚠️` · що потребує слова Романа ·
`Branch / HEAD / main не чіпався`.

## Якщо щось пішло не так

- **Конфлікт при push** → не `reset`, не force. `git pull --rebase origin <гілка>`,
  вирішити руками, пушити знову.
- **Сесія без комітів** (тільки обговорення) → Phase 0 і Phase 3 усе одно
  виконати: блок у `SESSION_LOG.md` з «Код не чіпали».
- **Два `/finish` підряд** → другий оновлює той самий блок і каже, що нового немає.
- **`start_head` недоступний** (немає ні runtime-файлу, ні блоку в HANDOFF) →
  взяти діапазон за `git log --since` і зазначити в звіті, що це наближення.
