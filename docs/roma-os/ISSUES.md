# Crow OS MP — баги

Життєвий цикл дефектів. Баги з iPhone і з CI живуть **тут**, а не
розчиняються в `SESSION_LOG.md`.

**Межа зі `STAGE-1.md`:** «ще треба перевірити на телефоні» — це чекбокс у
`STAGE-1.md §6`. Сюди запис потрапляє тоді, коли перевірили і знайшли
**конкретний дефект**. Не дублювати.

**Статуси:**

| status | Значення |
|---|---|
| `open` | відтворюється, не виправлено |
| `fixed` | виправлено в коді, але ще не перевірено на практиці |
| `verified` | перевірено там, де баг і проявлявся (телефон, CI, живий URL) |
| `wontfix` | свідомо лишаємо, з причиною |

`verified` не ставиться тільки тому, що код написано.

**Пріоритети:** `critical` (блокує роботу або ламає живий URL) ·
`high` · `medium` · `low`.

ID наскрізні: `ISS-001`, `ISS-002`, … Ротації немає — файл поки малий.

## Відкриті

ISS-002 і ISS-004 — `verified` зі скріншота живого iPhone 20.09 23:10. Решта

### ISS-002 — поле вводу ховається за барабаном на живому iPhone

- **status:** `verified`
- **priority:** `critical`
- **discovered:** 2026-09-20, живий URL на iPhone (скріншот Романа, екран «Події»)
- **area:** оболонка / `--tabbar-h`
- **actual behavior:** бар Crow стоїть на `bottom: calc(var(--tabbar-h) + 4px)`,
  але на телефоні `--tabbar-h` менша за реальну висоту `#tab-bar`
  (з safe area він ~101px, а не 67px, як без неї). Поле вводу на 25–30px
  заходить під барабан, видно тільки верхню смужку.
- **expected behavior:** поле вводу цілком над барабаном із зазором 4px,
  як у донора.
- **reproduction:** відкрити живий URL на iPhone (standalone), будь-який
  екран. У headless Chromium не відтворюється: там safe area = 0 і шрифти
  локальні, тож `--tabbar-h` збігається з висотою бару.
- **notes:** `measureChrome()` міряє бар у boot, у rAF, після `fonts.ready`
  і на `resize`. Якщо бар підростає пізніше (safe area, підміна шрифту),
  ніхто не переміряє. Донор (`boot.js:484–500`) має ще fallback через
  500 мс — при переносі його не взяли. Надійніше — `ResizeObserver` на
  `#tab-bar`, як уже зроблено для капсули барабана. Тест
  `the measured bar height reaches the CSS variable` цього не ловить: він
  перевіряє лише, що значення в межах 50–140.
- **fix commit:** `907291b` — boot.ts: ResizeObserver на `#tab-bar`/`#topbar`/полі вводу + fallback 500 мс, як у донора. Тест: змінна дорівнює реальній висоті і слідує за пізнім ростом бару.
- **verification:** headless Chromium 390px (e2e) ✅; живий iPhone ✅ — скріншот Романа 20.09 23:10, живий iPhone (standalone), екран «Події»: поле вводу цілком над барабаном, зазор ~4px.

### ISS-003 — `--dock-h` міряє весь бар разом зі схованим вікном чату

- **status:** `fixed`
- **priority:** `high`
- **discovered:** 2026-09-20, headless Chromium 390px під час розбору ISS-002
- **area:** оболонка / відступи екранів
- **actual behavior:** `measureChrome()` бере `#crow-ai-bar.offsetHeight`,
  а після переносу донорського бару всередині нього стоїть вікно чату,
  сховане `translateY(110%)`, а не `display:none`. Тож `--dock-h` = 427px
  замість ~62. Наслідки: `.screen` має `padding-bottom` 514px — після
  прокрутки до кінця під останнім записом стрічки ~250px порожнечі;
  `#toast-host` стоїть на 510px від низу, тобто посеред екрана.
- **expected behavior:** `--dock-h` = висота видимого поля вводу
  (`.ai-bar-input-box`, ~62px з відступом); екран закінчується одразу
  під останнім записом плюс бар і барабан.
- **reproduction:** живий URL або `npm run serve` → «Події» → прокрутити
  до кінця. `getComputedStyle(document.documentElement)
  .getPropertyValue('--dock-h')` → `427px`.
- **notes:** міряти `.ai-bar-input-box`, а не весь `#crow-ai-bar`.
- **fix commit:** `907291b` — `--dock-h` = висота `.ai-bar-input-box` + 4. Відступ екрана 141px замість 514. Тест: після прокрутки до кінця зазор до поля < 80px.
- **verification:** headless Chromium 390px (e2e) ✅; живий iPhone — ще ні

### ISS-004 — Crow у позі `front` зменшується і з'їжджає вниз

- **status:** `verified`
- **priority:** `high`
- **discovered:** 2026-09-20, живий URL на iPhone (скріншот Романа) + headless
- **area:** Crow / `character.ts`, `.crow-figure`
- **actual behavior:** слот персонажа `118×172`, `img` з `object-fit:
  contain` і `object-position: bottom`. `crow-front.webp` — `568×680`
  (пропорція 0.835): на висоті 172 він був би 144 завширшки, не влазить у
  118, тож малюється `118×141` і притискається донизу — голова на 31px
  нижче, ніж у позах `idle` (390×620) і `talk` (340×620), які влазять
  повністю. Після кожного повідомлення (`sayOnce`: talk → front) фігура
  помітно стрибає. Плюс зона 224px проти фігури 172px: ще 52px над
  головою. Разом голова стоїть на ~80px нижче верху бульбашки, тоді як у
  `mockup.html` голова на рівні верху бульбашки (фігура 228 у блоці 232).
- **expected behavior:** усі три пози однакової висоти 172px, без стрибка;
  голова на рівні верху бульбашки, як у мокапі.
- **reproduction:** відкрити застосунок, дочекатись кінця «розмови»
  (2.6 с) — поза `front`; порівняти з першими секундами (поза `talk`).
- **notes:** варіанти — слот під найширшу позу (`144px`; бульбашка звузиться
  до ~208px), або обрізати `crow-front.webp` до пропорції інших поз, або
  підняти фігуру до верху зони. Нахил 14° — свідомий параметр
  (`HANDOFF §3.5`: 10–20°), міняється одним числом у `board.ts`.
- **fix commit:** `3608e15` — Слот фігури = висота бульбашки × пропорція найширшої пози (`fitTo`), тож жодна поза не зменшується і не з’їжджає. Фігура тепер заввишки з бульбашку (рішення Романа 20.09), нахил 10°.
- **verification:** headless Chromium 390px (e2e) ✅; живий iPhone ✅ — той самий скріншот: поза `front` у стані спокою на повну висоту слота, голова на рівні верху бульбашки, фігура заввишки з бульбашку.

### ISS-005 — перемикання вкладки скидає прокрутку екрана на початок

### ISS-007 — згортання зони Crow різке і незрозуміле

- **status:** `fixed`
- **priority:** `high`
- **discovered:** 2026-09-20, живий iPhone (Роман), підтверджено по коду
- **area:** Crow / `board.ts`, `#crow-zone` CSS
- **actual behavior:** свайп угору по зоні спрацьовує лише на `touchend`
  (поріг 40px), без жодного руху під пальцем. У момент спрацювання
  `.crow-expanded` і `.crow-collapsed` міняються через `display:none` —
  персонаж, бульбашка і чіпи зникають миттєво, смужка з'являється миттєво,
  а зона (224 → 64px) і верх екрана (`--shell-top`) ще 0.28 с їдуть
  анімацією. Чіпи в згорнутому стані зникають зовсім. Свайп униз по
  згорнутій смужці не розгортає — swipe-detect стоїть тільки на
  `.crow-expanded`; розгортання лише тапом.
- **expected behavior:** згортання читається як один рух: те, що є на
  екрані, слідує за пальцем або хоча б плавно переходить у смужку; швидкі
  дії (чіпи) не пропадають.
- **reproduction:** будь-який екран → свайп угору по персонажу чи бульбашці.
- **notes:** у донора (`owl/board.js:61–67`) перемикання теж миттєве через
  `display`, але табло там маленьке й у потоці сторінки, тому не б'є в око;
  чіпи донор **лишає видимими** в обох станах (`chipsWrap.style.display =
  'flex'` завжди); свайп униз по розгорнутому табло у донора відкриває чат.
  Геометрія зони — наша (`HANDOFF §3.5`), донора для неї немає, тож і
  плавність — наше рішення. Варіанти: (A) cross-fade замість `display:none`
  синхронно з анімацією висоти + чіпи лишаються, як у донора; (B) зона
  слідує за пальцем і «защіпується» на порозі — той самий жест, що вже
  перенесений для вікна чату з `inbox-board.js`.

- **fix commit:** `3608e15` — Зона слідує за пальцем, защіпується на порозі 40px; смужка проявляється cross-fade; чіпи лишаються; свайп униз по смужці розгортає; свайп униз по табло відкриває чат.
- **verification:** headless Chromium 390px (e2e) ✅; живий iPhone — ще ні

### ISS-008 — e2e на WebKit падав на тесті оновлення живої Памʼяті

- **status:** `verified`
- **priority:** `high`
- **discovered:** 2026-09-21, CI (`ci.yml` run #58 на `a122d7b`, повтор run #61 на `1387373`)
- **area:** CI / e2e (WebKit) / оновлення живих даних
- **actual behavior:** на `main` після зрізу 1 job `e2e` червоний лише на
  WebKit, лише тест «a refresh redraws the screen you are looking at»:
  після синтетичного `visibilitychange` Памʼять не перемальовувалась.
  Дві причини по черзі: (1) headless WebKit тримає `document.visibilityState`
  не `visible`, і guard у `source.ts` блокував оновлення; (2) після того як
  service worker бере сторінку під контроль, Playwright у WebKit не бачить
  запити, які worker пропускає наскрізь, — підмінений `page.route()` gateway
  ставав недосяжним на другому fetch. Живий сайт не постраждав: обидва
  деплої зелені, Chromium зелений.
- **expected behavior:** оновлення при поверненні застосунку на екран
  перемальовує Памʼять; e2e доводить це обома двигунами.
- **reproduction:** push у `main` → `ci.yml` → job `e2e` з `PW_WEBKIT=1` → fail.
- **fix commit:** `8687330` — `pageshow` оновлює без перевірки видимості
  (сторінку показують — вона видима; bfcache-повернення не дає
  `visibilitychange`), `visibilitychange` і 90-секундний інтервал — лише на
  екрані; `f8c60b9` — `live.spec.ts` з `serviceWorkers: 'block'`, тест
  спершу перевіряє, що запит дійшов до gateway, окремий Chromium-тест
  доводить прохід worker'а.
- **verification:** `ci.yml` run #64 на `b301da1` — success усіма трьома
  job'ами (checks, gateway, e2e Chromium + WebKit), 2026-09-21 02:41.
